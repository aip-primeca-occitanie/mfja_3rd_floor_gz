Terminal Setup

Complete the supported Ubuntu, ROS, clone, dependency and first build steps in the root README before copying runtime commands from this page. A successful installation contains $HOME/mfja_3rd_floor_ros2_ws/install/setup.bash.

Build once after changing code, messages, config, or launch files. The commands use ${MFJA_WS:-$HOME/mfja_3rd_floor_ros2_ws}, so set MFJA_WS only if your workspace is somewhere else.

Sensor Names and Meaning

In code, every rail detector is the same binary sensor type. Use these names when reading the /room_315/rails/right/sensors/feedback or /room_315/rails/left/sensors/feedback topics. Shuttle Control: Move, Stop, Set Speed, or Go to a Slot

A shuttle moves automatically along its one-way rail route when it receives ON. Send OFF to stop it at its current position. Add a positive speed in metres per second to an ON command to choose the travel speed. Add target_slot to move to slot 1, 2, 3, or 4 and stop there automatically.

target_slot is a stop setpoint, not a route planner: it does not move any switch. The target must be reachable on the already selected route. The slot 1 to slot 3 example below relies on the fresh launch's all-EXTERIOR route; only a matching reached_target_slot confirms success.

Step 1: Launch One Stopped Shuttle

Terminal 1: Room 315 with one right shuttle
cd "${MFJA_WS:-$HOME/mfja_3rd_floor_ros2_ws}"
source /opt/ros/jazzy/setup.bash
source install/setup.bash

ros2 launch mfja_3rd_floor_bringup room_315_only.launch.py \
  robots:=none \
  start_paused:=false \
  gui:=true \
  enable_room315_kinematic_shuttles:=true \
  enable_room315_right_rail:=true \
  enable_room315_left_rail:=false \
  room315_right_shuttle_count:=1 \
  room315_right_start_slot:=1 \
  room315_shuttles_start_enabled:=false \
  room315_shuttle_speed:=0.2 \
  room315_show_device_markers:=true

Step 2A: Move Continuously, Stop, and Resume

State fieldMeaning
mode: MOVINGThe shuttle is travelling.
mode: DISABLEDThe drive is disabled initially, after OFF, or after target arrival. Check reached_target_slot to distinguish arrival.
reached_target_slot: '3'The controller reached slot 3 and stopped there.
mode: WAITINGThe shuttle is enabled but a stopper, another shuttle, or a motion guard is blocking it.

Commands are requests; wait for the state topic to report the requested actual state before continuing.

Do not reroute a moving or stopped shuttle in place. A shuttle can still occupy a branch or guard segment even after one stopper closes. Stop the current launch, restart with zero shuttles, change the coordinated pair, and confirm the state. Normal numbered start slots are on exterior guard segments, so an ordinary AddShuttle or RESET is not safe preparation for an INTERIOR route. Start motion only through a validated route-compatible scenario.

Sensors: Watch Live Rail Feedback

The sensors are binary: they report active: 1 when a shuttle is inside the sensor's configured radius_m, and active: 0 when that area is clear. For A*_STOPPER_SENSOR, the sensor point is derived from the matching stopper point minus before_stopper_m. Every reading uses sensor_type: sensor; shuttle_name identifies the detected shuttle when active. The segment, s, and s_ratio fields are privileged simulator/debug metadata, not additional physical sensor measurements. See Sensor Names and Meaning for the detector families. All sensor readings are published together on one topic: /room_315/rails/right/sensors/feedback.

Sensor and Stopper Positions: Edit Devices from the Terminal

Use room_315_device_position_tool.py when you have a desired Gazebo x/y/z point and want the YAML tool to convert it to the nearest rail segment plus s_ratio. The tool can update slots, position_sensors, and stoppers. Stopper-linked position sensors are derived from the matching stopper and before_stopper_m, so the tool does not write segment or s_ratio directly on them.

Get the target x/y/z from the Gazebo pose inspector, from a temporary reference model, or from a known point you want the device to snap near. Use --side left for rail_devices_left.yaml and --side right for rail_devices_right.yaml.

Stopper-linked sensor rule: to move A1_STOPPER_SENSOR, A2_STOPPER_SENSOR, A3_STOPPER_SENSOR, or A4_STOPPER_SENSOR, move the matching stopper in stoppers or edit before_stopper_m. Edit radius_m only when you want a larger or smaller detection area.

Step 1: Dry Run the Closest Rail Position

Start with no --write. The tool prints the closest rail segment, computed s_ratio, projected Gazebo point, and distance from your target. If the distance is above --max-distance-m, the tool refuses to write unless you explicitly add --force.

Dry run: convert Gazebo XYZ
cd "${MFJA_WS:-$HOME/mfja_3rd_floor_ros2_ws}"
source /opt/ros/jazzy/setup.bash
source install/setup.bash

ros2 run mfja_robot_control_config room_315_device_position_tool.py \
  --side left \
  --x -10.50 \
  --y -4.20 \
  --z 0.84

Step 2: Move a Normal Position Sensor

Use --category position_sensors for DZI* and DA* detectors. Add --write only after the dry-run distance looks reasonable.

For DZI* entries, sensor feedback follows the entry's segment, s_ratio, and radius_m. Older custom files may still contain descriptive index_zone or start_slot labels, but those labels do not move the detector.

Move DA2EL

  --y -4.20 \
  --z 0.84 \
  --category position_sensors \
  --name DA2EL \
  --write

Robot Control: Topics, Names, and Interfaces

The configured robots are controlled through ROS topics bridged to Gazebo. Fixed-base robots use /<robot_name>/joint_trajectory. TIAGo variants also have /<robot_name>/cmd_vel for mobile-base motion. For tiago_base, /joint_trajectory is only for the existing torso joint; there is no arm or head to command. The helper robot_joint_command.py accepts --unit rad or --unit deg. Degree inputs are converted to radians for angular joints; linear joints such as torso_lift_joint stay in meters.

The joint helper reads the live state, rejects non-finite or out-of-range targets, and publishes one densely sampled minimum-jerk trajectory instead of an instantaneous position step. The model-side smooth controller limits every joint to 50% of its SDF velocity limit and holds the completed pose exactly under gravity. If --duration is too short for those limits, motion takes longer rather than exceeding the allowed speed. Direct one-point JointTrajectory commands are also interpolated smoothly. Rebuild and restart Gazebo after controller or model changes because the system plugin is loaded when the robot model is created.

The four industrial robots have an independent symmetric gripper command. Use robot_gripper_command.py instead of adding jaw positions to the six arm joints. How the percentages map to position

CommandTargetMeaning
open 100q100Configured fully-open position
close 100q0Configured fully-closed position
open 50q0 + 0.5 * (q100 - q0)Midpoint
close 50q100 - 0.5 * (q100 - q0)The same midpoint
open 0q00% of the opening action
close 0q1000% of the closing action
With no percentage, open uses default_open_percentage and close uses default_close_percentage from the YAML file. Both shipped defaults are 100%, but they can be changed independently for each robot. The percentage is the amount of the named action, so close 25 closes one quarter of the travel and leaves the gripper at 75% of its open range.

Configure what 0% and 100% mean

Edit the existing robot entry in the YAML; keep the other robot entries. Positions are per-jaw prismatic positions in meters. Therefore the total change in jaw-to-jaw opening is twice position_at_100_percent_m - position_at_0_percent_m. The 0% value must be zero or greater, and 100% must be greater than 0%.

Example Staeubli range and bare-action defaults
# File: mfja_robot_control_config/config/gripper_command_defaults.yaml
# Edit this entry inside the existing grippers: mapping.
# This is a partial snippet; do not replace the complete file with it.
  staubli1:
    position_at_0_percent_m: 0.0
    position_at_100_percent_m: 0.010
    default_open_percentage: 75.0
    default_close_percentage: 100.0

In this example, open without a number targets 75% of the configured range, open 100 targets 10 mm per jaw, and close returns to 0 mm. Restart Gazebo after saving the file. A workspace built with --symlink-install does not need another build for this YAML-only edit; a copied installation does.
