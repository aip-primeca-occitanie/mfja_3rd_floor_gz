\section{CAD modelling and Gazebo integration strategy}

I iteratively exported my Autodesk Inventor third-floor design to Gazebo. The
earliest retained stage exposed a missing room, incorrect door dimensions,
incomplete windows, an unsuitable ground plane and a mesh-orientation error. I
revised the source CAD rather than hiding those discrepancies with unrelated
Gazebo offsets, then added the furniture and static contents of both furnished
rooms. I created the dedicated Room~315 shell and assembled its workstations,
guards and supplied rail-cell parts. The attributed robot geometry was reused;
my work was its adaptation, placement and integration.

The robot-body assets have package-level provenance. KUKA uses
\path{kuka_kr6_support} \citep{rosindustrialkuka}. Stäubli uses
\path{staubli_tx2_60_support} and shared TX60 meshes
\citep{rosindustrialstaubli,rosindustrialstaublitx60}. Both Yaskawa variants
use \path{motoman_hc10_support} \citep{rosindustrialmotoman}. TIAGo uses
\path{tiago_description} from the Tiago-Harmonic fork of PAL Robotics'
\path{tiago_robot} \citep{tiagoharmonic}. I adapted these assets through local
URDF/SDF wrappers, paths and simulator integration; I did not create their
robot-body geometry.

Each asset required consistent units, origin, pose, visual material and
an explicit collision-model decision. CAD origins are often inconvenient
manufacturing datums, while Stereolithography (STL) files contain no unit
metadata. Explicit scale and orientation checks therefore aligned the visual
geometry and, where enabled, the collision geometry with the intended room
coordinates. Integration proceeded in three stages:

\begin{enumerate}
  \item load each asset alone and verify scale, orientation and reference frame;
  \item decide whether collision geometry was required, then place the asset in
  common coordinates; and
  \item integrate it in the full scene and add static path/SDF checks.
\end{enumerate}

Static room and rail-cell assets retain collision geometry where needed. The
four industrial-arm models omit it for deterministic debugging, so they cannot
test contact or collision avoidance.

\paragraph{Engineering iteration.}
The first useful check was not visual similarity at one camera angle, but whether
known room features kept the same scale, orientation and relative position when
loaded separately and in the complete world. A failed check returned the work to
the Autodesk Inventor export or to the explicit SDF transform, depending on
whether the discrepancy belonged to the source geometry or its simulation
placement. After integration, static tests checked referenced assets, the
deliberate presence or absence of collision elements and initial robot joints.
This process produced a traceable final scene. No independent metrology was
available to quantify geometric error.

\section{Repository refactoring}

ROS~2 organises software into packages \citep{ros2packages}. As the project
grew, I split the flat layout into four of them: description assets, user-facing
bring-up, typed rail interfaces and control/configuration. This separates
reusable interfaces from their implementation and lets bring-up compose the
system without owning control algorithms. \code{colcon} is the workspace build
tool \citep{colcon}; I used it to keep the workspace selectively buildable.
\cref{fig:packages} shows the declared internal package dependencies and
\cref{app:technical} lists the package contents.

The initial flat package was adequate while it held only a world and a few
assets, but adding robot wrappers, rail control, custom messages, planning,
perception and tests made ownership ambiguous. In particular, a launch package
that also defined message types or controller code would force unrelated users
to depend on the complete research stack. I therefore kept models and worlds in
the description package, made the public rail contracts independently buildable,
placed runtime implementations and tests in control/configuration, and reserved
bring-up for composition. After the move, I checked resource paths, package
dependencies and the retained launch profiles from a clean build. The refactor
did not change runtime message direction; it made build-time ownership and
handover boundaries explicit.

\section{Model integration}

For each fixed-base arm, integration preserved the vendor link--joint tree and
aligned its visual geometry with the controller joint list. TIAGo required a
different composition because
its mobile base, torso, arm and head expose several control groups rather than
one fixed-base arm. These differences motivated the common access layer in
\cref{chap:multi-robot} without pretending that all robots share one command
surface.

\section{Launch profiles and reproducibility}

ROS~2 provides a configurable package launch system \citep{ros2launch}. I used
it to reuse one Room~315 argument set for full-floor, Room-only and
isolated-robot modes. Operators select robots, shuttles, cameras, markers,
initial slots and graphical or headless operation; research components require
explicit activation. These profiles isolate an integration boundary or scale
without changing public namespaces; their entry points, runbook and status are
indexed in \cref{app:technical,chap:results}.

The Ubuntu~24.04, ROS~2 Jazzy and Gazebo Harmonic workspace installs the recorded
runtime. The full-floor smoke covers startup and interface availability;
\cref{app:reproducibility} gives the build record.

\section{Conclusion}

The retained third-floor and Room~315 scenes now load through reproducible
profiles with integrated robot assets. Static checks and the six-robot
cold-start confirmed loading, isolated names and fresh feedback. The main
difficulty was aligning CAD units and origins while documenting each
collision-model decision.
