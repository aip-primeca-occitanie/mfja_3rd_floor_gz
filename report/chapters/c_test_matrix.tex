\section{Protective boundary cases}

The required response is no actuation when critical facts are unknown, stale or
contradictory, or when semantic JSON contains plans or commands. The same
response applies to occupied targets without a clearance proof,
insufficient headway, switch changes within \SI{0.35}{m}, capacity overflow,
planner timeout, unsupported actions, stale effect observations, the absence of
an eligible payload-qualified shuttle, and unavailable or hash-mismatched model
weights. Each condition blocks command publication and state mutation based on
unverified, unauthorised or stale evidence.

\section{Interpretation of integrated evidence}

Each automated family targets a specific software layer. The integrated
campaign in \cref{chap:results} complements those checks with 12 isolated
cold starts of the live ROS graph. The six cases on each rail cover all eight
shuttle identities and five predeclared case families. The preserved evidence
binds the source tree, launch declarations, runtime configuration and model
artifacts to per-case logs, ROS bags and terminal-effect verification.

Each declared condition was executed once. Repetitions across controlled seeds
would quantify run-to-run variation, while a separate live-graph campaign could
extend the layered automated fault tests with stale vision, sensor loss, planner
timeout, emergency stop and conflicting goals.
Offline visual metrics continue to provide a separate evaluation of perception.
