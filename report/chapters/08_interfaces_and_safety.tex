\chapter[Typed Interfaces, Contracts and Safety Supervision]
{Typed Interfaces, Contracts and\\Safety Supervision}
\label{chap:interfaces}

I implemented typed contracts to separate task intent, commands, state reports
and observed effects. The supervision layer uses those contracts to reject
stale or conflicting state, protect shared routes and verify command effects.

Using standard ROS~2 interfaces and my Phase~1 rail simulator, I designed and
tested the typed contracts, sparse-update rules, reservations, software command
checks and effect verification; none of this supervision layer was present in
the baseline.

\section{Typed and versioned contracts}

ROS~2 uses \code{.msg}, \code{.srv} and \code{.action} definitions for
messages, request--response services and long-running goals
\citep{ros2jazzyinterfaces}. I used these definition types for the rail
interface. They keep four roles distinct: a
\emph{task} states the requested outcome, a \emph{command} requests a device
change, \emph{state} reports what the controller observes, and a \emph{result}
records whether the expected effect was established. A PDDL effect is only the
planner's predicted change; the executive must confirm the corresponding
simulator state from newer reports.

Switch and stopper commands are sparse named updates. For example,
\code{switches: \{A3: INTERIOR\}} changes only A3; an omitted name retains its
current value. After validation, the supervisor converts this checked envelope,
represented in JavaScript Object Notation (JSON), to a typed \code{SwitchCommand},
\code{StopperCommand} or \code{ShuttleCommand}. Training labels and translator
metadata are never accepted as live commands.

Operational records also use versioned schemas that constrain fields and
types, record identifiers, timestamps and provenance, and restrict which
component may produce each record. Incompatible versions and unauthorised
producers are rejected before planning or command publication. The principal
contract catalogue and producer matrix are retained in
\cref{app:technical}; \cref{fig:contract-semantics} shows the two rules most
important at runtime.

\section{Accepted state and software supervision}

Observed facts retain four explicit statuses: \emph{known}, \emph{unknown},
\emph{stale} and \emph{conflicting}. Only fresh, authorised and consistent known
facts may populate an executable planning state; a missing reading is therefore
not interpreted as false or as free space. The gateway combines the confirmed
task with accepted visual, device and identity-bearing sensor reports while
keeping learned estimates separate from exact simulator state and test-only
providers.

The rule-based \code{room\_315\_vla\_supervisor.py}---not a learned VLA
policy---gives final software authorisation. It validates sparse JSON commands
against rail state, then publishes typed commands consumed by the kinematic
controller.

Before publication it checks:

\begin{itemize}
  \item latched emergency-stop state and the immediate global \code{stop\_all}
  operation; command structure, identity and rail-side consistency;
  \item fresh/non-conflicting state, occupied targets, reservation-block
  ownership, geometric separation and block headway;
  \item switch change within the \SI{0.35}{m} protected distance;
  stopper and route-clearance state;
  \item post-command occupancy by another shuttle, sensor dropout, timeout,
  unknown localisation, impossible pose or \code{FALLING} mode;
  \item a configured recovery-retry limit (default two) and lexicographic
  reservation-conflict tie-breaking.
\end{itemize}

Diagnostics retain metrics, recent decisions and each authorisation/rejection
reason; rejection leaves the device unchanged. Exceptions or shutdown during
an active goal trigger gateway \code{stop\_all}.

Reservations give one shuttle/task temporary ownership of a route block, while
geometric headway independently prevents overlap. A crossed-ownership conflict
uses deterministic identity priority; the other shuttle stops, observes and
replans. Switch changes are additionally blocked when fresh controller
coordinates place a shuttle within the protected rail distance. This handles
the declared conflict pattern, not arbitrary wait-for cycles or temporal
non-progress; the detailed resource and feedback rules are in
\cref{app:technical}.

\section{Effect verification and emergency handling}

The runtime defines the expected effects of every translated execution
command. Examples include:

\begin{itemize}
  \item \code{SET\_SWITCHES}/\code{SET\_STOPPERS}: requested values match
  controller status;
  \item commanded slot motion: two consecutive identity-bearing DZI readings,
  controller
  \path{reached_target_slot}, explicit \code{DISABLED} state and required
  confirmation frames agree;
  \item \code{STOP\_NOW}: controller reports a fresh explicit
  \code{DISABLED} state;
  \item observation-only inspection: a newer visual observation is
  available after the request.
\end{itemize}

Results retain command, plan-step and observed-state identifiers; motion effects
also record command-linked observations and require newer reports for arrival
and retries. Switch/stopper matching permits \emph{cached state}: the last
accepted value may predate the command, unlike post-command motion checks.

Manual device-debug commands use normal structural/supervisor checks. The
exception is emergency: it immediately invokes all-shuttle \code{stop\_all}
without planner state and latches rejection of motion until explicit clearing.
Stoppers can thus be tested without a language model but remain subject to the
same software checks.

\section{Conclusion}

The typed messages and rule-based supervisor now connect task intent to checked
commands and observed effects; \cref{chap:results} reports their verification.
The main difficulty was combining partial device updates arriving at different
times without treating missing values as false. Complex deadlocks, stalled tasks
and machinery-safety certification are outside this supervisor's scope.
