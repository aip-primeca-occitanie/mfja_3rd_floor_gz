\chapter{Unified Multi-Robot Access and Control}
\label{chap:multi-robot}

Six different robot models had to run together without losing their
model-specific command interfaces. I linked a shared registry and instance
selector to isolated communication links and a common command tool.

Using the project-supplied inventory and the robot models attributed in
\cref{chap:digital-twin}, I designed and tested a registry in YAML, a
human-readable configuration format.
I also implemented selector rules, isolated namespaces, bridge generation, the
launcher and the command helper; none of this shared access layer was present in
the baseline.

\section{What ``unified'' means}

Here, \emph{unified} means that one YAML registry declares selectable instances,
one launch path starts them and their bridges, one separate helper validates a
named robot and joint vector, and instance-derived namespaces isolate commands
and feedback.

A joint trajectory is a timed sequence of joint targets. Fixed-base arms use
these trajectories, whereas TIAGo also exposes base velocity and a linear torso
joint. The helper validates the selected robot, vector and units without hiding
these model-specific interfaces.

\section{Multi-robot operation in one Gazebo process}

Each selected YAML entry defines an instance name, model, pose and enabled
state. Launch rejects duplicate names and derives its namespace and bridge from
that identity; the helper supplies the corresponding joint order, topic and
units. Selection, spawning, commands and feedback therefore share one identity
chain. The retained smoke covers all six robots, while automated tests cover
the remaining selector forms (\cref{chap:results}).

\section{Configuration-driven robot registry}

Selectors accept a full name, alias, numeric order, set, \code{all} or
\code{none}; the retained instances and their principal command surfaces are

order, topics and unit semantics. This remaining duplication is test-covered,

\section{Dynamic bridge generation}

\code{ros\_gz\_bridge} translates between Gazebo Transport and ROS~2 messages
\citep{gazeborosintegration}. In my implementation, launch derives one bridge
lane per selected YAML identity. Commands enter Gazebo and required state,
odometry and transforms return on that lane, preserving one-to-one addressing
(\cref{fig:robot-flow}).

Deriving the bridge from the selected registry entry is important: a renamed
instance changes its spawned entity, ROS namespace and bridge topics together.
A hand-written bridge list could leave one of those three names stale and route
a valid command to the wrong model. The loader therefore rejects duplicate
instances before spawn, and tests compare the selected identity with the topics
created for it.

\section{Joint-command helper}

The helper validates robot identity, position count, joint mapping and units
before namespaced publication; it does not plan trajectories, collision-free
motion or cell synchronisation. Typed boundaries allow another provider to
preserve identity, units, timestamps and feedback. Usage and provenance are in
\cref{app:reproducibility}.

Publishing a raw \code{JointTrajectory} remains possible, but the helper removes
two common operator ambiguities: the order of the numeric positions and whether
an angular value is expressed in degrees or radians. Linear joints remain in
metres. A rejected vector produces no publication, while a valid vector is sent
only to the selected instance namespace.

The retained six-instance cold start verifies distinct, fresh feedback for the
fourth.

\paragraph{Portability boundary.}

The public identity, command and feedback contracts are independent of the
Gazebo mesh and could be preserved by a future hardware provider. Implementing
that provider was outside this work.

\section{Conclusion}

The resulting access layer starts six isolated robot instances without hiding
their command differences. The 42-check suite and cold-start smoke confirmed
selector behaviour, distinct names and fresh feedback
(\cref{chap:results}). The main integration difficulty was preserving one
identity chain across different joint counts, units and mobile-base interfaces.
