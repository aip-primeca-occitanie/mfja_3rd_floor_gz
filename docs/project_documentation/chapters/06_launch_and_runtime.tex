\section{Base Gazebo Composition}

\file{mfja_robot_control_config/launch/multi_robot_sim.launch.py} performs the
following work in order:

\begin{enumerate}
  \item Resolve the selected world and read its internal entity name.
  \item Optionally write an obstacle-free temporary world without modifying the
        checked-in source.
  \item Prepend the description model directory to
        \code{GZ_SIM_MODEL_PATH} and \code{GZ_SIM_RESOURCE_PATH}.
  \item Set the selected Gazebo transport partition.
  \item Start the Gazebo server; add \code{-r} only when the profile is not paused.
  \item Start \file{mfja_robot_control_config/scripts/conveyor_loop_mode_controller.py}
        as the visual switch sink.
  \item Optionally start the Gazebo GUI with the selected GUI config.
  \item After three seconds, bridge \rosname{/clock} and the world
        \code{set_pose}, \code{create}, and \code{remove} services.
  \item Load, validate, select, and spawn every requested robot; generate its
        bridge mapping and start its namespaced state publisher.
\end{enumerate}

The full-floor profile starts paused. Simulation-time timers, trajectory
controllers, rail motion, delayed switch/stopper updates, and many freshness
checks do not advance until Gazebo is unpaused.

\begin{warningbox}[What the high-level VLA switch does not start]

primitive supervisor; it can also start the recorder. It does not start the

gateway. Those remain separate, artifact-dependent launches listed in

\section{Singleton Locks and Namespace Isolation}

The floor composition locks
\file{/tmp/mfja_room315_floor_runtime.lock} with \code{fcntl.flock}. Only one
high-level Room 315/full-floor process is supported on one host because the rail
ROS names and world services are fixed. A unique Gazebo \code{GZ_PARTITION}
isolates transport, but does not rename the ROS graph.

A lock pathname may remain after a clean shutdown; the operating-system lock is
released when the descriptor closes. Do not delete or bypass the lock while an
owner is alive. Stop the owner. The task-execution node has a second singleton
lock at \file{/tmp/mfja_room315_task_execution_node.lock} to prevent concurrent
gateways. The owning sources are
\file{mfja_3rd_floor_bringup/launch/room_315_floor_common.py} and
\file{mfja_robot_control_config/scripts/room_315_task_execution_node.py}.

\section{Shutdown Semantics}

For an actuating rail task, send a controlled \state{OFF} or supervisor
\code{stop_all}, wait for explicit \state{DISABLED} feedback, stop interactive
helpers, then press Ctrl-C in the high-level launch. The task gateway publishes
\code{stop_all} during exception or shutdown handling when an active goal
exists. Ctrl-C should propagate so the floor lock releases and child processes
exit. The owning implementation is
\file{mfja_robot_control_config/scripts/room_315_task_execution_node.py},
\file{mfja_robot_control_config/scripts/room_315_closed_loop_executive.py}, and
\file{mfja_3rd_floor_bringup/launch/room_315_floor_common.py}.
