\section{Repository Boundary and Directory Classification}

The repository root is a meta-repository, not a ROS package: there is no root
\file{package.xml}. Colcon should discover the four explicit package roots, not
reports, extracted datasets, presentation material, or generated output.

\section{Package: mfja\_rail\_interfaces}

This package deliberately has the smallest dependency surface. Its
\file{mfja_rail_interfaces/CMakeLists.txt} invokes
\code{rosidl_generate_interfaces}; its manifest depends on
\code{builtin_interfaces}, \code{std_msgs}, the ROSIDL generator, and the
ROSIDL runtime. It contains no node or business logic.

\begin{itemize}
  \item \file{mfja_rail_interfaces/msg/NamedState.msg} is the name/value unit
        used by switch and stopper command/state arrays.
  \item Shuttle command/state and add-service definitions own shuttle lifecycle
        and exact-target wire semantics.
  \item Sensor definitions own binary occupancy plus simulator debug metadata.
  \item Visual definitions own the accepted perception contract; they are not
        aliases for controller state.
\end{itemize}

Changing an interface is a compatibility change. Rebuild this package and all
consumers; update serializers, dataset schemas, tests, and this manual. Never
edit generated Python/C++ bindings in \file{build/} or \file{install/}.

The package manifest declares the core ROS/CV/PlanSys2 surface, including
Torch/TorchVision. Torch is optional for base simulation even though it is a
runtime dependency for advanced tools. Internal Python imports rely on the
installed program directory or a source \code{PYTHONPATH}; shared foundation
modules such as
\file{mfja_robot_control_config/scripts/room_315_visual_state_dataset.py},
\file{mfja_robot_control_config/scripts/room_315_multi_shuttle.py},
\file{mfja_robot_control_config/scripts/room_315_rail_defaults.py}, and
\file{mfja_robot_control_config/scripts/room_315_contracts.py} have many
consumers and require broad tests when changed.

The CMake \code{PROGRAMS} list is broader than the intended public CLI because
it also installs importable support modules. Verify the public surface with
\code{ros2 pkg executables}; do not infer it from the CMake list alone. Four
tracked scripts are intentionally absent from that list:

\begin{itemize}
  \item \file{mfja_robot_control_config/scripts/room_315_experiment_a_smoke_v2_package.py};
  \item \file{mfja_robot_control_config/scripts/room_315_visual_final_test_v4.py};
  \item \file{mfja_robot_control_config/scripts/room_315_visual_v4_final_test_coverage_compat.py}; and
  \item \file{mfja_robot_control_config/scripts/room_315_visual_v4_final_test_coverage_extension.py}.
\end{itemize}

Do not advertise these files through \code{ros2 run} unless an explicit install
rule, dependency review, and installed-surface test are added. Chapter
\ref{ch:installation} explains the resulting install and stale-overlay traps.

\section{Package: mfja\_3rd\_floor\_bringup}

The bringup package keeps operator commands stable while lower-level launch
implementation evolves:

\begin{itemize}
  \item \file{mfja_3rd_floor_bringup/launch/room_315_only.launch.py} selects
        the focused running profile;
  \item \file{mfja_3rd_floor_bringup/launch/full_floor.launch.py} selects the
        complete paused profile;
  \item \file{mfja_3rd_floor_bringup/launch/single_industrial_robot.launch.py}
        forwards a bounded selector to the isolated lower-level launch; and
  \item \file{mfja_3rd_floor_bringup/launch/room_315_floor_common.py} owns
        shared arguments, the singleton lock, obstacle-cache clearing, and
        delayed rail and perception-and-safety includes.
\end{itemize}

The package installs its launch directory as a whole. A new launch file is
installed after rebuild, but every new argument still needs validation,
wrapper forwarding, tests, \code{--show-args} verification, and documentation.

\section{Dependency Rules and Known Exception}

Lower layers must not import user-facing bringup policy. Interfaces should not
depend on control logic; description assets should not depend on planning; and
pure data/contract helpers should stay importable without ROS when designed
that way. This direction keeps geometry and tests usable offline and prevents a
research runtime from becoming mandatory for a base simulation.

One current packaging defect breaks that intended direction at runtime:
\file{mfja_robot_control_config/launch/room_315_runtime_acceptance.launch.py}
resolves and includes
\file{mfja_3rd_floor_bringup/launch/room_315_only.launch.py}, while the control
manifest does not declare bringup. Adding that dependency directly would create
a cycle because bringup already depends on control. The acceptance launch
therefore requires all four packages to be installed. Move the top-level
acceptance composition into bringup, or extract shared composition into a lower
package, rather than formalizing the cycle. Treat this exception as a defect,
not a precedent.
