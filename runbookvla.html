Quick Map: What VLA Means Here

Supervisor

Receives JSON on /room_315/vla/command, runs the safety decoder, then converts accepted event-level commands into switch, stopper, and shuttle commands.

action_vector safety decoder status JSON

Cameras

One independent overhead RGB-D camera per rail side. These images feed the recorder and the external VLA agent.

right_rail_rgbd left_rail_rgbd

Dataset / Benchmark

The recorder writes episodes and event-level labels. The benchmark runner dispatches task templates to generate demos and metrics.

events.jsonl training_events metrics

Multi-Shuttle Benchmark

Room 315 now has a scaffold for up to four shuttles per rail side. Stable identities are R1..R4 for right_shuttle_1..right_shuttle_4 and L1..L4 for the left rail. Existing one-shuttle demos remain compatible.

Launch four shuttles per side

source /opt/ros/jazzy/setup.bash
source install/setup.bash

ros2 launch mfja_3rd_floor_bringup room_315_only.launch.py \

  start_paused:=false \
  gui:=true \
  enable_room315_kinematic_shuttles:=true \
  enable_room315_vla:=true \
  room315_right_shuttle_count:=4 \
  room315_right_start_slots:=1,2,3,4 \
  room315_left_shuttle_count:=4 \
  room315_left_start_slots:=1,2,3,4
When a side has more than one shuttle, shuttle-motion commands must include a shuttle identity such as R2, right_shuttle_2, or room315_right_shuttle_2. Ambiguous motion is rejected by the supervisor.

Action schema v3 adds shuttle_index, shuttle-specific target_id values, fleet reason IDs, and coordination_mode. This is still the event-level target. The model-facing input remains only language, overhead_images, and last_command.

Shuttle identity markers are configured in config/room_315_vla/shuttle_identity.yaml. Labels and perimeter fiducials are mounted outside the center payload zone so identity remains visible under partial payload occlusion. Fiducial detections and identity tracks are privileged metadata for safety, debugging, and evaluation; they are not copied into model_input.

PDDL / PlanSys Scenario Generation

The focused research pipeline uses PDDL with a real PlanSys2 planner as an expert scenario-generation layer. PDDL goals become PlanSys2 symbolic plans, symbolic plans become primitive VLA commands, and those commands are executed only through the existing VLA supervisor. The learned model never sees PDDL facts or plans as input.

Pipeline: PDDL goal/problem to symbolic_plan to primitive commands such as switches, stoppers, shuttle ON/OFF, and DONE. The supervisor safety decoder gates every command, the dataset recorder writes events.jsonl, and the model target remains action_vector.
CategoryFieldsPolicy use
Model inputlanguage, overhead_images, last_commandAllowed input to the learned VLA policy.
Targetaction_vectorPreferred event-level model output.
PDDL / identity metadataplanning_source, pddl_goal, pddl_problem, symbolic_plan, plan_step_index, target_shuttle_id, visible_marker_count, payload_presentGeneration and evaluation provenance only. Not model input.
Privileged stateprivileged_eval, structured_rail_state, observation.stateAudits, ablations, and evaluation only.

PlanSys2 backend

plansys is the only supported planner backend. The generator sends the Room 315 PDDL domain and selected problem text to the PlanSys2 /planner/get_plan service, normalizes the returned timed plan into symbolic steps, then translates those steps into primitive VLA commands and action_vector labels. There is no deterministic fallback planner in runtime generation.

What the Recorder Writes

Path inside an episodeMeaningUse for training?
episode.json Episode summary: ID, task, frame count, event count, success/failure, and safety metrics. No. Use for inspection and bookkeeping.
events.jsonl Main training file. Each JSON line is a decision event: image/language/last_command before the decision, then action and action_vector. Yes. This is the important training file.
data.jsonl Framewise raw replay. It stores detailed frame state for audit and may repeat the same command over multiple frames. No. Do not use as supervised labels.
images/right_rail_rgb/*.jpg Right camera JPEG frames. Yes, through references in events.jsonl.
images/left_rail_rgb/*.jpg Left camera JPEG frames. Yes, through references in events.jsonl.

Important Fields in events.jsonl

FieldMeaning
model_input_schema_versionCurrently 3.
model_input.languageThe language goal or task text.
model_input.overhead_imagesReferences to camera images allowed for the model.
model_input.last_commandThe previous command; this is allowed model input.
actionReadable event-level symbolic command such as SET_SWITCHES or SHUTTLE_ON.
action_vectorThe same command encoded as a vector using action_space.yaml. This is the preferred model output.
planning_source, pddl_goal, symbolic_plan, target_shuttle_id, visible_marker_count, payload_presentPDDL and identity/occlusion provenance. Useful for reports and replay, not model input.
structured_rail_stateReadable rail state snapshot for auditing and ablations only. Not model input.
privileged_evalExpert sensor/state data for evaluation and auditing only. Not model input.
observation.stateState vector for ablation/debug only. Do not use for the main visual policy input.
Bottom line: train on events.jsonl, and make the model output action_vector or direct primitive JSON. Do not train on data.jsonl, and do not use privileged_eval or structured_rail_state, PDDL metadata, or observation.state as input for the main policy.
